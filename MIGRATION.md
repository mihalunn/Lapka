# Перевод Lapka на рельсы AI-инженерии (harness + SDD)

Статус: точка входа в процесс, v1.  
Владелец: Михаил Долгов.  
Дата: 2026-10-06.

Аудитория: агент (Cursor) и владелец. Продуктовые требования живут в
`docs/product/*`; этот документ описывает только процесс разработки и миграцию
процесса.

## 0. Как пользоваться

- Агент начинает любую работу с чтения этого документа и `AGENTS.md`.
- Единица работы — один виток: одно проверенное изменение, задача из backlog или
  её часть.
- Фазы идут строго последовательно. Не начинать фазу N+1, пока не закрыты
  критерии фазы N.
- Контрольные точки из раздела 7 требуют остановки и подтверждения владельца.
- Каждая фаза заканчивается зелёным `npm run check` и коммитом, а не настройкой
  без результата.
- Если ответа нет в указанных документах, агент останавливается и спрашивает, а
  не додумывает.

## 1. Текущее состояние на 2026-10-06

- Репозиторий: `github.com/mihalunn/Lapka`, ветка `main`, два коммита.
- Код: каркас Vite + React + TypeScript.
- Есть `eslint.config.js` и базовые scripts Vite.
- Нет Prettier, Stylelint, Vitest, Testing Library, MSW, Husky, CI и единой
  команды проверки.
- Продуктовый слой готов: `docs/product/01–06` содержит brief, границы MVP,
  анализ, UX/UI-спецификацию, архитектуру, backlog и DoD.
- Нет `AGENTS.md`, ADR, specs задач, task state, progress-памяти и
  версионируемых промптов.

Репозиторий пока непрозрачен для агента: вход хаотичен, знания находятся вне
репозитория, тестов нет, критерий готовности неформален. Цель миграции —
agent-ready репозиторий.

Ограничения владельца: вечера по 2–3 часа; стажировка LAD/Astro — приоритет №1;
Lapka — полигон AI-инженерии; высокий риск выгорания, поэтому действует принцип
ship over configure.

## 2. Целевое состояние

| Компонент harness | Где живёт в Lapka                                                   |
| ----------------- | ------------------------------------------------------------------- |
| Контекст          | `AGENTS.md` → `docs/ai-context/` → `docs/product/`                  |
| Спецификации      | `docs/specs/T-XXX.md` из задач `docs/product/06-backlog.md`         |
| Решения           | `docs/adr/ADR-XXX.md`                                               |
| Инструменты       | npm scripts, MSW, Vitest                                            |
| Проверки          | тесты, `npm run check`, DoD из `06-backlog.md`                      |
| Память            | `docs/state/progress.md`, `docs/state/current-task.md`, git-история |
| Наблюдаемость     | витки в `progress.md`, evals-чеклист владельца                      |
| Ограничения       | разделы 7 и 10 этого документа                                      |

Критерий целевого состояния: агент берёт задачу, прочитав только `AGENTS.md` →
spec → указанные в spec документы; заканчивает виток зелёным `npm run check` и
записью в `progress.md` без напоминаний владельца.

## 3. Принципы

1. Один виток — одно проверенное изменение.
2. Тесты до реализации (RED → GREEN) для критериев приёмки задачи.
3. Scope guard: новое попадает в задачу, только если без этого не проходит
   главный сценарий.
4. Контекст — минимальный, достаточный для правильного решения.
5. Память — это отбор и структура; чат не является памятью.
6. Сначала harness, затем автономность.
7. Человек участвует в контрольных точках.
8. Заявление агента «готово» не является доказательством; доказательство —
   зелёные проверки и ревью.

## 4. План миграции

### Фаза 0. Фундамент harness (T-002)

1. Создать ветку `chore/harness-foundation` от `main`.
2. До установки показать владельцу зависимости и новые scripts. После
   подтверждения установить Prettier, Stylelint, Vitest,
   `@testing-library/react`, `@testing-library/jest-dom`, jsdom и добавить
   scripts `lint`, `format`, `stylelint`, `test`, `typecheck`, `check`.
3. Проверить, что намеренные lint-ошибка, type-ошибка и падающий тест
   обнаруживаются, затем удалить ошибки. Показать результат и дождаться
   подтверждения.
4. Создать `AGENTS.md` по шаблону раздела 5.
5. Выполнить `npm run check`, создать коммит и merge в `main` только после
   подтверждения владельца.

Критерий фазы: `npm run check` существует, проходит на каркасе и падает на
ошибке. Husky и pre-commit в Фазе 0 не устанавливаются.

### Фаза 1. Контекстный слой и память

1. Создать `docs/ai-context/product.md` — выжимку `01` и `02`: идея, аудитория,
   главный цикл, границы MVP, scope guard.
2. Создать `docs/ai-context/architecture.md` — выжимку `05`: стек, границы
   состояний, этапы хранения A (MSW) → B (backend), формат API-контракта.
3. Создать `docs/ai-context/conventions.md`: структура папок, CSS Modules,
   токены, нейминг, коммиты и порядок импортов. Агент предлагает, владелец
   утверждает.
4. Создать шаблон ADR и ADR-001 — ADR-004: состояние, моки, стили, формы.
5. Создать `docs/state/progress.md` и `docs/state/current-task.md`.
6. Не создавать `docs/prompts/` до Фазы 2.
7. Дополнить `AGENTS.md` ссылками. Владелец читает каждый ai-context и ADR перед
   merge.

Критерий фазы: на вопрос о границе серверного и клиентского состояния агент
отвечает по `AGENTS.md` → ai-context без сканирования репозитория.

### Фаза 2. Промпты и спеки под версией (L2)

1. Создать `docs/prompts/new-feature.md` с ролью, ссылками на контекст и spec,
   пайплайном и форматом ответа.
2. Создать `docs/prompts/bug-fix.md` и `docs/prompts/review.md`.
3. Создать `docs/specs/T-003.md` по шаблону. Владелец утверждает spec до старта.

Критерий фазы: T-003 запускается только через `new-feature.md` и утверждённую
spec.

### Фаза 3. Первый SDD-цикл

1. Пройти полный виток раздела 8 для T-003.
2. Закрыть DoD из `06-backlog.md`.
3. Записать виток в `progress.md`, обновить `current-task.md`.
4. Повторять цикл для следующих задач backlog по порядку.

Критерий фазы: три задачи подряд прошли цикл без переписывания агентского кода
владельцем с нуля. Правки по ревью допустимы.

### Фаза 4. Наблюдаемость и evals

1. Использовать trace витка в `progress.md`; внешние инструменты не подключать.
2. После каждой задачи владелец заполняет evals-чеклист раздела 9.
3. Раз в месяц проверять актуальность ai-context и ADR, устаревшие решения
   помечать `superseded`.

Критерий фазы: по `progress.md` восстанавливается, что произошло и почему, за
последние три витка без обращения к чатам.

### Фаза 5. Автономность

После трёх чистых циклов Фаз 3–4 разрешить агенту ограниченные фоновые задачи в
sandbox: обновить `progress.md`, добавить тест к существующему коду, подготовить
черновик spec. Контрольные точки раздела 7 сохраняются.

Цель — экономически оправданная автономность при приемлемой цене ошибки, а не
максимальная автономность.

## 5. Шаблоны

### AGENTS.md

```markdown
# AGENTS.md — точка входа для агентов в Lapka

## Что это

## Где что лежит

## Как брать задачу

## Пайплайн витка

## Жёсткие запреты

## Если ты не знаешь

## Команды
```

### Spec

```markdown
# Spec T-XXX: <название>

Статус: draft | approved | in-progress | done

## Цель

## Критерии приёмки

## Что читать

## Что НЕ трогать

## Проверка

## Риски / заметки
```

### ADR

```markdown
# ADR-XXX: <решение>

Дата: YYYY-MM-DD. Статус: proposed | accepted | superseded by ADR-YYY

## Контекст

## Решение

## Последствия
```

### Запись прогресса

```markdown
## Виток N — YYYY-MM-DD — T-XXX

- Контекст: spec и ссылки.
- Решения: 1–3 ключевых пункта.
- Проверки: npm run check → OK | FAIL.
- Статус: done | review | blocked.
- Время: ~N ч.
```

### Текущая задача

```markdown
# Текущая задача

Задача: T-XXX <название>. Spec: docs/specs/T-XXX.md
Фаза витка: spec | tests | impl | verify | review
Готово: <пункты>.
Следующий шаг: <одно предложение>.
Блокеры: нет | <что>.
```

## 6. Правила памяти

- `progress.md` ведётся append-only; устаревшее не удаляется, а помечается
  `superseded: <причина>`.
- `current-task.md` перезаписывается при смене задачи.
- Всё важное из чатов с агентом переносится в `progress.md` или ADR в тот же
  вечер.
- Длинная сессия чата не является памятью; память — файлы.

## 7. Контрольные точки

Обязательное подтверждение владельца требуется перед:

1. установкой или добавлением зависимостей;
2. правками `docs/product/*`;
3. новым ADR или изменением принятого решения;
4. merge в `main`;
5. удалением файлов или папок;
6. работой с секретами и `.env`;
7. расширением scope задачи.

Без дополнительного согласования агент может работать в sandbox: рабочая ветка,
тесты и код в рамках утверждённой spec, `progress.md`, `current-task.md`.

## 8. Единый виток

1. Намерение: владелец называет номер задачи из backlog.
2. Спецификация: агент создаёт draft spec, владелец утверждает её.
3. Контекст: агент читает `AGENTS.md` → spec → ссылки из spec.
4. Тесты: агент пишет тесты на критерии, запускает и получает RED.
5. Реализация: минимальный код до GREEN.
6. Проверка: `npm run check` и DoD из backlog.
7. Память: запись в `progress.md`, обновление `current-task.md`.
8. Ревью: владелец смотрит diff; затем правки или коммит и merge после
   подтверждения.

## 9. Evals-чеклист владельца

После каждой задачи оценить по шкале 0–5:

1. Агент понял задачу без уточнений сверх spec?
2. Использовал нужные документы и не выдумал контракты?
3. Тесты появились до реализации?
4. `npm run check` запущен без напоминания?
5. `progress.md` восстанавливает ход решений?

Тренд вниз по трём задачам подряд означает, что нужно чинить harness: контекст,
правила или spec, а не менять модель.

## 10. Запреты агенту

- Реализация до тестов на критерии приёмки.
- Сканирование всего репозитория вместо маршрутов из `AGENTS.md`.
- Новые зависимости без подтверждения.
- Правки `docs/product/*` по инициативе агента.
- Расширение scope задачи.
- Закомментированный код, `console.log`, моки в production-коде.
- Завершение витка без `npm run check` и записи в `progress.md`.
- Самостоятельный merge в `main`.
- Работа с секретами и `.env` без контрольной точки.

## 11. Первый шаг

Выполнить Фазу 0:

1. создать ветку `chore/harness-foundation`;
2. показать владельцу зависимости и scripts;
3. после подтверждения настроить harness и доказать RED/GREEN;
4. после повторного подтверждения создать `AGENTS.md`;
5. остановиться перед коммитом и merge.
