# Учебный backlog

Задачи идут вертикальными шагами: после каждого этапа приложение остаётся запускаемым и показывает осмысленный результат. Оценки ориентировочные и нужны только для ограничения объёма.

## Definition of Done для каждой задачи

- поведение соответствует критериям приёмки;
- TypeScript, lint и тесты проходят;
- есть состояния loading, empty и error, если задача получает данные;
- интерфейс проверен клавиатурой;
- интерфейс проверен на ширинах 390, 768, 1024 и 1440 px;
- отсутствует горизонтальная прокрутка страницы;
- нет реальных персональных данных;
- решение кратко описано в PR или учебном дневнике.

## Подготовка визуальной системы

### D-001. Зафиксировать дизайн-контракт

**Результат:** согласованы токены, контрольные ширины и адаптивные правила из UX/UI-спецификации.

**Критерии:** разработчику не требуется самостоятельно выбирать цвета, отступы, радиусы или расположение основных блоков.

### D-002. Проверить три опорных wireframe

**Результат:** обзор семьи, страница питомца и календарь описывают основной сценарий на mobile, tablet и desktop.

**Критерии:** понятны приоритет контента, перестроение колонок и положение навигации; отдельные финальные макеты всех страниц не требуются.

## Итерация 0. Основа проекта

### T-001. Создать репозиторий и каркас

**Результат:** Vite-приложение React + TypeScript запускается локально.

**Критерии:** настроены scripts для dev/build/test/lint; добавлены базовые README и `.env.example`; секретов нет.

**Оценка:** 1 вечер.

### T-002. Подключить качество кода

**Результат:** ESLint, Prettier, Stylelint, Vitest и Testing Library дают понятную обратную связь.

**Критерии:** намеренная ошибка обнаруживается соответствующим инструментом; команды описаны в README.

**Оценка:** 1 вечер.

### T-003. Перенести дизайн-токены

**Результат:** цвета, отступы, радиусы и типографика объявлены CSS custom properties, а служебная страница `/ui-kit` показывает используемые foundations.

**Критерии:** значения соответствуют UX/UI-спецификации; demo-блок использует только токены; проверен контраст основных сочетаний.

**Оценка:** 1 вечер.

## Итерация 1. Прочитать данные питомца

### T-004. Настроить маршрутизацию и AppLayout

**Результат:** доступны `/overview`, `/pets/:petId`, `/calendar`, `/family`.

**Критерии:** активный пункт навигации заметен; неизвестный путь показывает NotFound; переходы работают без перезагрузки.

**Оценка:** 1–2 вечера.

### T-005. Описать типы и mock fixtures

**Результат:** подготовлены вымышленные данные семьи, двух питомцев, записей и событий.

**Критерии:** fixtures соответствуют доменным типам; связи используют устойчивые id; данные разных питомцев различимы.

**Оценка:** 1 вечер.

### T-006. Подключить MSW и базовый API layer

**Результат:** `GET /api/pets` и `GET /api/pets/:petId` работают как HTTP-запросы.

**Критерии:** можно включить задержку и ошибку; RTK Query хранит серверный кэш; компоненты не импортируют fixtures напрямую.

**Оценка:** 2 вечера.

### T-007. Собрать обзор семьи

**Результат:** пользователь видит питомцев и ближайшие события.

**Критерии:** карточка ведёт на правильный `petId`; реализованы loading, empty, error; layout соответствует макетам desktop, tablet и mobile.

**Оценка:** 2 вечера.

### T-008. Собрать сводку питомца

**Результат:** `/pets/:petId` показывает профиль, ближайшее событие и последние записи.

**Критерии:** изменение URL загружает другого питомца; неправильный id показывает NotFound; данные не смешиваются; композиция соответствует всем адаптивным макетам.

**Оценка:** 2 вечера.

## Итерация 2. Добавить запись истории

### T-009. Спроектировать форму записи

**Результат:** статическая доступная форма содержит поля из UC-02.

**Критерии:** каждое поле имеет label; порядок tab логичен; обязательность видна не только по цвету.

**Оценка:** 1 вечер.

### T-010. Подключить React Hook Form и Zod

**Результат:** форма проверяет обязательные поля и дату.

**Критерии:** сообщения стоят рядом с полями; после ошибки значения не теряются; focus переходит к первой ошибке.

**Оценка:** 1–2 вечера.

### T-011. Реализовать mock mutation создания записи

**Результат:** `POST /api/pets/:petId/entries` возвращает созданную запись.

**Критерии:** submit блокируется на время запроса; серверная ошибка показана; после успеха список истории обновляется.

**Оценка:** 2 вечера.

### T-012. Добавить одно mock-вложение

**Результат:** пользователь выбирает разрешённый файл и видит его имя и размер.

**Критерии:** ограничения формата и размера видимы; неверный файл не отправляется; в репозиторий не добавляются реальные документы.

**Оценка:** 1 вечер.

## Итерация 3. Запланировать событие

### T-013. Собрать календарный список

**Результат:** события сгруппированы по месяцу и отфильтрованы по питомцу.

**Критерии:** фильтр отражён в query-параметре; есть пустое состояние; даты локализованы; строки событий корректно перестраиваются на mobile.

**Оценка:** 2 вечера.

### T-014. Добавить форму события

**Результат:** пользователь создаёт будущее событие по UC-03.

**Критерии:** прошедшая дата отклоняется; событие появляется в календаре и сводке питомца; ошибки API обработаны.

**Оценка:** 2 вечера.

### T-015. Завершить событие

**Результат:** planned-событие становится completed и предлагает создать запись истории.

**Критерии:** данные события предзаполняют форму записи; пользователь может отказаться; повторное завершение невозможно.

**Оценка:** 2 вечера.

## Итерация 4. Полировка вертикального сценария

### T-016. Проверить основной сценарий тестами

**Результат:** интеграционный тест проходит путь «питомец → запись → событие».

**Критерии:** тест взаимодействует по ролям и доступным именам; не проверяет внутреннее состояние компонентов.

**Оценка:** 1–2 вечера.

### T-017. Провести ручную accessibility-проверку

**Результат:** основной сценарий проходится с клавиатуры и при увеличении масштаба.

**Критерии:** focus виден; заголовки последовательны; ошибки объявляются; нет ловушки фокуса.

**Оценка:** 1 вечер.

### T-018. Опубликовать demo

**Результат:** приложение и README доступны по публичной ссылке.

**Критерии:** прямое открытие вложенного маршрута работает; ограничения mock-версии описаны; есть скриншоты и список архитектурных решений.

**Оценка:** 1 вечер.

## Первый практический шаг

Начинать следует только с T-001. Перед установкой библиотек нужно самостоятельно объяснить:

1. что делает Vite;
2. чем runtime dependency отличается от dev dependency;
3. какие команды нужны для запуска и production build.

После T-001 полезно остановиться и проверить, что созданный каркас понятен, прежде чем добавлять Redux, формы и моки.
