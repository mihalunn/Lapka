# Пользовательские сценарии и предметная модель

## Роли MVP

| Роль | Возможности | Ограничения |
| --- | --- | --- |
| Владелец пространства | Управляет питомцами, записями, событиями и списком участников | В MVP не настраивает отдельные права |
| Участник семьи | Просматривает и изменяет питомцев, записи и события | Не удаляет семейное пространство |
| Демонстрационный пользователь | Проходит приложение без реальной регистрации | Данные могут сбрасываться |

Равные права на содержимое — упрощение MVP. Полноценную модель доступа следует проектировать только вместе с настоящей авторизацией и backend.

## Основные сценарии

### UC-01. Выбрать питомца и увидеть сводку

**Предусловие:** в семейном пространстве есть хотя бы один питомец.

1. Пользователь открывает приложение.
2. Видит список питомцев и ближайшие общие события.
3. Выбирает питомца.
4. Видит основные сведения, ближайшие события и последние записи этого питомца.

**Результат:** пользователь понимает текущее состояние дел по питомцу.

**Особые состояния:** питомцев нет; карточка загружается; данные не загрузились.

### UC-02. Добавить медицинскую запись

**Предусловие:** выбран питомец.

1. Пользователь начинает добавление записи.
2. Выбирает тип «Визит к врачу».
3. Указывает дату, заголовок и описание.
4. При необходимости указывает клинику и прикрепляет файл.
5. Проверяет введённые данные и сохраняет.
6. Новая запись появляется в хронологии выбранного питомца.

**Результат:** факт визита доступен всей семье.

**Правила:** питомец, дата, тип и заголовок обязательны; дата записи не должна быть позднее текущего момента; ограничения формата и размера файла задаёт API-контракт.

### UC-03. Запланировать событие

**Предусловие:** выбран питомец.

1. Пользователь открывает календарь или действие «Запланировать».
2. Выбирает питомца, тип события, дату и время.
3. Добавляет название и необязательную заметку.
4. Сохраняет событие.
5. Событие появляется в календаре и сводке питомца.

**Результат:** все участники видят ближайшее дело.

**Правила:** дата нового события должна быть в будущем; питомец, дата, время и название обязательны.

### UC-04. Завершить событие и сохранить результат

**Предусловие:** существует запланированное событие.

1. Пользователь открывает событие.
2. Отмечает его выполненным.
3. Выбирает, нужно ли создать запись в истории.
4. При согласии форма записи получает дату, питомца и название из события.
5. Пользователь дополняет и сохраняет запись.

**Результат:** план закрыт, а произошедшее отражено в истории без повторного ввода основных данных.

### UC-05. Добавить второго питомца

1. Пользователь открывает список питомцев.
2. Заполняет обязательные сведения новой карточки.
3. Сохраняет карточку.
4. Новый питомец появляется в переключателе.
5. Его история и календарные события изначально пусты.

**Результат:** данные питомцев разделены и не смешиваются.

## Ключевые пользовательские истории

- Как член семьи, я хочу выбрать питомца и увидеть последние события, чтобы быстро понять актуальную ситуацию.
- Как член семьи, я хочу записать результат визита к врачу, чтобы позднее восстановить историю лечения.
- Как член семьи, я хочу запланировать будущее дело, чтобы остальные участники знали о нём.
- Как член семьи, я хочу превратить выполненное событие в запись истории, чтобы не вводить сведения дважды.
- Как владелец, я хочу добавить ещё одного питомца, чтобы вести их данные раздельно.

## Связи

- одно семейное пространство содержит участников и питомцев;
- питомец содержит записи истории и календарные события;
- запись и событие принадлежат только одному питомцу;
- выполненное событие может быть связано максимум с одной записью;
- вложение в MVP принадлежит одной записи.

## Важные инварианты

- каждый запрос к данным питомца проверяет принадлежность семейному пространству;
- переключение питомца меняет все зависимые данные интерфейса;
- удаление питомца не должно происходить без предупреждения о связанных данных;
- время хранится в ISO 8601, а показывается в локальном формате пользователя;
- вес хранится числом в килограммах, единица отображается интерфейсом;
- клиент не считается источником истины для прав доступа.
