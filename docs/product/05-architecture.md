# Техническая концепция

Решения относятся к учебной frontend-версии. Они выбраны после определения сценариев, а не ради количества технологий.

## Формат приложения

**SPA** подходит для Lapka, потому что приложение представляет авторизованный личный кабинет с частыми переходами между связанными данными без необходимости перезагружать документ.

Публичные SEO-страницы в MVP отсутствуют. Если позже появится публичная карточка питомца или контентный раздел, для них можно отдельно рассмотреть SSR/Next.js; сейчас это добавит сложность без пользы.

## Рекомендуемый frontend-стек

- **React + TypeScript** — основной изучаемый стек и строгие контракты данных.
- **Vite** — минимальная и прозрачная сборка без необходимости изучать внутренности framework.
- **React Router** — маршруты и вложенный layout приложения.
- **Redux Toolkit + RTK Query** — кэш серверных данных, запросы и инвалидация; обычные slices добавляются только для действительно глобального клиентского состояния.
- **React Hook Form** — управление формами без большого количества ручных обновлений.
- **Zod** — единые схемы проверки форм и ответов mock API.
- **Mock Service Worker** — реалистичные HTTP-моки до появления backend.
- **CSS Modules** — изолированные стили и практика вёрстки без дополнительной UI-библиотеки.
- **Vitest + Testing Library** — проверки пользовательского поведения.
- **ESLint + Prettier + Stylelint** — обратная связь до code review.

Не следует добавлять Redux slice для каждой сущности. Данные API живут в RTK Query; открытое состояние формы — в React Hook Form; локальное визуальное состояние — в компоненте.

## Маршруты

```text
/
├── /overview
├── /pets/new
├── /pets/:petId
├── /pets/:petId/edit
├── /pets/:petId/entries/new
├── /pets/:petId/entries/:entryId
├── /calendar
├── /events/new
├── /events/:eventId
└── /family
```

На первом учебном шаге `/` перенаправляет на `/overview`, а пользователь считается вошедшим под demo-account.

## Границы состояния

### Серверное состояние — RTK Query

- семейное пространство;
- участники;
- питомцы;
- записи истории;
- события;
- результаты create/update/delete.

### Глобальное клиентское состояние — Redux slice только при необходимости

- активное семейное пространство, когда пространств станет больше одного;
- глобальные уведомления интерфейса.

Выбранного питомца лучше кодировать в URL (`:petId` или query-параметр), чтобы ссылка была воспроизводимой.

### Локальное состояние React

- раскрытие небольшого меню;
- видимость подтверждения;
- временный выбор фильтра, если он не должен сохраняться в URL.

### Состояние формы

- значения полей;
- touched/dirty;
- клиентские ошибки;
- состояние отправки.

## Этапы хранения

### Этап A — frontend на моках

MSW перехватывает запросы, а данные берутся из fixtures. Изменения хранятся в памяти вкладки и сбрасываются при перезагрузке. Это честное ограничение нужно написать в demo.

`localStorage` допустим только как отдельное учебное улучшение для несекретных демоданных. Файлы, персональные сведения и токены авторизации там хранить нельзя.

### Этап B — настоящий backend

Предполагаемая инфраструктура:

- REST API;
- реляционная база данных для семей, пользователей, питомцев, записей и событий;
- объектное хранилище для вложений;
- cookie-based session или иной механизм, выбранный вместе с backend;
- проверка доступа к `familySpaceId` на сервере.

Конкретный backend-стек пока не фиксируется: это отдельное решение после готового frontend-сценария.

## Черновой API-контракт

Базовый формат списка:

```json
{
  "data": [],
  "meta": {
    "total": 0
  }
}
```

Одна сущность:

```json
{
  "data": {}
}
```

Ошибка:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте заполненные поля",
    "fieldErrors": {
      "title": "Введите название"
    }
  }
}
```

### Питомцы

- `GET /api/pets`
- `POST /api/pets`
- `GET /api/pets/:petId`
- `PATCH /api/pets/:petId`
- `DELETE /api/pets/:petId`

### История

- `GET /api/pets/:petId/entries?type=&cursor=`
- `POST /api/pets/:petId/entries`
- `GET /api/pets/:petId/entries/:entryId`
- `PATCH /api/pets/:petId/entries/:entryId`
- `DELETE /api/pets/:petId/entries/:entryId`

### Календарь

- `GET /api/events?petId=&from=&to=&status=`
- `POST /api/events`
- `GET /api/events/:eventId`
- `PATCH /api/events/:eventId`
- `DELETE /api/events/:eventId`
- `POST /api/events/:eventId/complete`

### Семья

- `GET /api/family`
- `GET /api/family/members`

Настоящие приглашения и управление участниками не входят в первый API.

## Поток добавления записи

```text
Форма
  → проверка Zod
  → RTK Query mutation
  → MSW / будущий API
  → ответ с созданной записью
  → инвалидируется список истории питомца
  → переход к странице питомца
```

## Структура frontend по ответственности

```text
src/
├── app/          # store, router, providers, глобальные стили
├── pages/        # маршруты и сборка экранов
├── widgets/      # крупные самостоятельные части страниц
├── features/     # пользовательские действия и формы
├── entities/     # Pet, TimelineEntry, CalendarEvent
├── shared/       # UI, API base, utilities, config
└── mocks/        # MSW handlers и fixtures
```

Эта структура — ориентир, а не требование создать все папки заранее. Новый слой или модуль появляется только вместе с первой реальной ответственностью.

## Безопасность и приватность

- только вымышленные demo-данные в репозитории;
- проверка расширения файла на клиенте не заменяет серверную проверку MIME и размера;
- сервер выдаёт доступ к вложениям только участникам нужной семьи;
- HTML из пользовательских данных не рендерится напрямую;
- секреты не попадают в `VITE_*` переменные;
- удаление медицинской записи требует подтверждения;
- для реального продукта необходимы политика хранения и удаление аккаунта с данными.

## Архитектурные решения, которые пока не нужны

- Next.js;
- микрофронтенды;
- GraphQL;
- WebSocket;
- офлайн-first и сложная синхронизация;
- собственная библиотека компонентов как отдельный package;
- оптимистические обновления до появления измеримой задержки.
