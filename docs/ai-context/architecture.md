# Архитектурный контекст Lapka

Статус: утверждено владельцем 2026-10-07.

Источник истины: `docs/product/05-architecture.md`. Этот файл содержит только
решения, необходимые агенту для выбора правильной границы ответственности.

## Формат и стек

Lapka — SPA на React и TypeScript, собираемая Vite. Публичных SEO-страниц в MVP
нет.

Целевой frontend-стек:

- React Router для маршрутов и вложенного layout;
- Redux Toolkit и RTK Query для серверного кэша;
- React Hook Form для состояния форм;
- Zod для схем форм и проверки ответов mock API;
- Mock Service Worker для HTTP-моков;
- CSS Modules и CSS custom properties для стилей;
- Vitest и Testing Library для пользовательских тестов.

Библиотека подключается только в задаче, где она впервые нужна. Наличие
библиотеки в целевом стеке не разрешает устанавливать её без контрольной точки
из `MIGRATION.md`.

## Границы состояния

### Серверное состояние — RTK Query

- семейное пространство и участники;
- питомцы;
- записи истории;
- события;
- результаты create, update и delete.

API-данные не дублируются в обычных Redux slices.

### Глобальное клиентское состояние — Redux slice

Slice создаётся только для состояния, которое действительно разделяется
несколькими несвязанными частями приложения. Предварительные кандидаты:

- активное семейное пространство, когда пространств станет больше одного;
- глобальные уведомления интерфейса.

Выбранный питомец кодируется в URL через `:petId` или query-параметр, а не
хранится отдельной копией в Redux.

### Локальное состояние React

- небольшие раскрытые меню;
- видимость подтверждения;
- временный фильтр, если он не должен сохраняться в URL.

### Состояние формы — React Hook Form

- значения полей;
- touched и dirty;
- клиентские ошибки;
- состояние отправки.

## Этапы хранения

### Этап A — frontend на моках

MSW перехватывает HTTP-запросы, данные поступают из fixtures. Изменения живут в
памяти вкладки и сбрасываются после перезагрузки. Компоненты не импортируют
fixtures напрямую.

`localStorage` не является базовым хранилищем MVP. Его можно рассматривать
только как отдельное учебное улучшение для несекретных демоданных. Файлы,
персональные данные и токены там не хранятся.

### Этап B — backend

После завершения frontend-сценария моки заменяются REST API, реляционной базой,
объектным хранилищем вложений и серверной проверкой доступа к
`familySpaceId`. Конкретный backend-стек пока не выбран.

## API-форматы

Список:

```json
{
  "data": [],
  "meta": {
    "total": 0
  }
}
```

Одна сущность:

```json
{
  "data": {}
}
```

Ошибка:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте заполненные поля",
    "fieldErrors": {
      "title": "Введите название"
    }
  }
}
```

Новые поля, endpoint и правила ошибок нельзя придумывать. Если продуктовые
документы их не определяют, требуется spec или решение владельца.

## Структура по ответственности

Ориентир:

```text
src/
├── app/
├── pages/
├── widgets/
├── features/
├── entities/
├── shared/
└── mocks/
```

Пустые слои заранее не создаются. Папка или модуль появляется вместе с первой
реальной ответственностью.

## Приватность и безопасность

- использовать только вымышленные demo-данные;
- не рендерить пользовательский HTML напрямую;
- не считать клиент источником истины для прав доступа;
- не помещать секреты в `VITE_*`;
- проверка файла на клиенте не заменяет серверную проверку MIME и размера;
- удаление медицинской записи требует подтверждения.
